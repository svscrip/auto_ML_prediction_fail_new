## Текст выступления

**[Открыть README в ветке `yanshin`.]**

Здравствуйте. Представляю учебный проект классификации
отказов промышленного оборудования и его доработку по трём домашним заданиям.
За основу взят код из `main` группового проекта. Моя работа находится в отдельной
ветке `yanshin`; основную ветку я не изменял. В README собраны ссылки на результаты
каждого задания, поэтому их можно проверить непосредственно в репозитории.

Бизнес-идея проекта — помочь инженеру определить, какие наблюдения требуют
проверки в первую очередь. Время специалистов ограничено, а пропущенный отказ
может привести к простою. Поэтому важна не только метрика модели, но и то,
как её результат используется при принятии решения об обслуживании.

**[Показать `src`, `pyproject.toml`, `poetry.toml`, `.gitignore`.]**

Первое задание связано с подготовкой ML-проекта к сопровождению. В исходной
версии уже были выделены модули загрузки данных, построения признаков,
обучения, инференса и мониторинга. Я сохранил эту структуру и проверил её
работу, затем исправил конкретные ошибки на границах этих модулей.

Poetry управляет зависимостями и создаёт отдельное окружение `.venv` внутри
проекта. В `pyproject.toml` описаны требования и группа инструментов разработки,
а `poetry.lock` фиксирует конкретные версии. Команда `poetry sync --with dev`
восстанавливает их. В отличие от одного только `venv`, Poetry дополнительно
решает задачу зависимостей и lock-файла. Сам каталог окружения не попадает в
Git: сохраняются настройки, по которым его можно воспроизвести.

**[Открыть `.pre-commit-config.yaml` и `.github/workflows/ci.yml`.]**

Перед коммитом запускаются Black, isort и Flake8: первый форматирует код,
второй упорядочивает импорты, третий обнаруживает нарушения стиля и часть
ошибок. Дополнительные хуки проверяют YAML, TOML, конфликтные маркеры и ключи.
Версии инструментов согласованы с Poetry. Те же проверки и pytest запускаются
в CI; для моей ветки добавлен запуск по push. Локальные хуки устанавливаются
командой `poetry run pre-commit install`.

Из практических исправлений выделю четыре. Во-первых, проверка входных данных
теперь отклоняет бесконечные значения, некорректные флаги и дубли идентификаторов
строк. Во-вторых, одинаковые вероятности больше не вызывают ошибку квантильных
границ. В-третьих, расчёт PSI корректно учитывает минимальные значения и нулевые
частоты. В-четвёртых, при несовпадении путей MLflow выдаёт объяснение и сохраняет
историю экспериментов, вместо автоматического удаления базы. Для этих случаев
добавлены регрессионные тесты. Пути данных и артефактов можно задавать через
переменные окружения. Повторная проверка также исправила JSON-отчёты для
малых пакетов и запуск этапов: после ошибки обучения инференс не запускается.

**[Открыть `model_card.md`, разделы 1, 4, 5 и 9.]**

Второе задание — карточка модели и описание её роли. Карточка построена по
структуре Google: назначение, сведения о модели, факторы, метрики, обучающие
и проверочные данные, анализ результатов, этические аспекты и ограничения.

Используется CatBoost для бинарной классификации. Входные данные — пять
числовых параметров оборудования, тип изделия и флаги режимов отказа.
После преобразований модель получает 17 признаков, из которых шесть
передаются как категориальные.
Для каждой строки сохраняются оценка вероятности класса «отказ» и категория
риска. Отдельный CSV содержит сводные рекомендации по правилам, например
по износу; это ещё не персональный план ремонта каждого станка.
Категория «Высокий» означает оценку выше 90-го процентиля данного пакета,
а не вероятность отказа выше 90 процентов. Данные синтетические, из
Kaggle Playground S3E17, а не исходные десять тысяч строк AI4I.

В карточке сохранён проверяемый исторический снимок полного прогона исходной
версии. На валидационной части он показывает ROC-AUC около 0,97 и recall
около 0,86 при пороге классификации 0,5. Этот порог используется для расчёта
бинарных метрик и не задаёт категории риска.
Но precision составляет только около 0,28: на 371 верное обнаружение приходится
967 ложных тревог и 59 пропусков. Поэтому одной высокой AUC недостаточно для
решения о внедрении. Стоимость лишних проверок и пропущенных отказов нужно
согласовать с владельцем процесса.

Есть и более существенное ограничение. Флаги режимов отказа описывают уже
произошедшее событие, поэтому могут давать утечку целевой информации. Счётчик
отказов рассчитывается до разделения выборки и не является подтверждённой
временной историей. Кроме того, та же валидация используется для early stopping —
выбора числа деревьев. Это не независимый финальный тест.
Я прямо указал эти ограничения: текущая модель — учебная базовая версия, а не
доказанная система раннего предупреждения. Для такого применения нужны
данные с временными метками, корректный горизонт прогноза, признаки без
утечки и отдельная независимая оценка.

**[Открыть `Model_BPMN.md` и показать схему.]**

На схеме показан путь от поступления измерений до решения инженера и обратной
связи. ML нужен для проверки гипотезы, что нелинейные сочетания температуры,
износа и нагрузки позволяют лучше распределять проверки, чем простое правило
или календарный план. После оценки моделью инженер анализирует результат,
при необходимости оформляет обслуживание, а фактический исход возвращается
в данные для контроля качества.

Польза должна измеряться снижением простоев и лишних проверок при одинаковой
нагрузке специалистов. Реальных стоимостей и результатов пилота у меня нет,
поэтому я не заявляю денежную экономию. В документе есть способ её будущей
оценки и явно отделены реализованные CSV-операции от проектируемой интеграции
с производством.

**[Открыть `Model_retrain_BPMN.md`.]**

Третье задание — проект будущего процесса переобучения. В нём запуск предусмотрен
по дрейфу входных данных, снижению качества на подтверждённых исходах, расписанию или
ручному запросу. Например, предлагается проверять PSI от 0,25 в двух
последовательных суточных окнах минимум по тысяче наблюдений. Это проектное
условие, а не уже работающий триггер или доказательство необходимости замены модели.

По этой схеме сначала проверяются источник и достаточность новых размеченных
данных. Далее фиксируется снимок, выполняются подготовка и обучение новой версии.
Кандидат сравнивается с действующей моделью на одной выборке. Помимо AUC
учитываются recall, стоимость ошибок, подгруппы и эксплуатационные ограничения.
Порог классификации выбирается заранее на валидационной выборке.
Для итогового сравнения нужна отдельная выборка, которая не участвовала в настройке.

После автоматических проверок решение принимает валидатор и владелец
процесса. Они проверяют применимость модели и допустимость последствий ошибки.
Только после одобрения версия регистрируется и проходит тестовое развёртывание.
При неуспехе сохраняется прежняя модель или выполняется откат. Результат
фиксируется в аудите и направляется через предусмотренное Telegram-уведомление.

Для защиты от бесконечного цикла предусмотрены максимум три попытки,
обязательный анализ причины и прекращение повторов без новой гипотезы.
Отсутствие ответа валидатора за 24 часа не считается согласием: публикация
останавливается и вопрос эскалируется.

Сейчас реализованы обучение, MLflow Tracking и расчёт показателей мониторинга.
Реестр промышленных версий модели, согласование, автоматический деплой и Telegram
ещё не подключены. Tracking хранит эксперименты, но сам по себе не означает
допуск модели к эксплуатации. Задание на проектирование выполнено схемой и описанием.

## Короткие ответы на возможные вопросы

| Вопрос | Ответ |
| --- | --- |
| Зачем Poetry, если есть venv? | venv изолирует Python-пакеты; Poetry дополнительно описывает, разрешает и фиксирует зависимости в lock-файле. |
| Почему `.venv` нет на GitHub? | Окружение зависит от ОС и интерпретатора. В Git хранятся рецепты его восстановления, а не установленные бинарные пакеты. |
| Почему CatBoost? | Он уже выбран в групповом baseline и подходит для табличных данных с категориальными признаками. Его превосходство над другими алгоритмами в моей доработке заново не доказывалось. |
| Разве 0.97 AUC не достаточно? | Нет: есть утечка, дисбаланс, слабая калибровка и 967 ложных тревог при пороге 0.5. Нужна независимая оценка и стоимость решений. |
| Чем отличаются recall и precision? | Recall: найдено 371 из 430 реальных отказов, то есть около 86%. Precision: из 1 338 тревог верны 371, то есть около 28%. Это разные знаменатели. |
| Зачем оставлена модель с утечкой? | Для этих заданий сохранён исходный baseline, а работа сосредоточена на сопровождении, карточке и процессах. Утечка названа препятствием для промышленного применения. Для пилота нужно отдельно обучить и оценить вариант без неё. |
| PSI доказывает ухудшение модели? | Нет, это сдвиг входных распределений. Качество проверяется по фактическим исходам, причины сдвига анализируются. |
| Что означает «Высокий» риск? | Оценку строго выше 90-го процентиля пакета; это не вероятность ≥90% и не производственный порог безопасности. При совпадающих оценках в этой категории может оказаться меньше 10% строк, в том числе ни одной. |
| Когда новая модель выигрывает? | По проекту: AUC не ниже 0.90 и прирост минимум 0.005, нижняя 95% граница разницы выше нуля; дополнительно ограничения recall, стоимости, нагрузки и совместимости, затем одобрение человека. Числа — предложенные условия, не действующий production-регламент. |
| Не подгоняется ли модель к оценке при трёх попытках? | В спецификации повторы требуют свежего evaluation snapshot либо отдельного финального отложенного теста. Порог и параметры не подбираются по финальному тесту. |
| Где реализован автоматический retraining? | В этой сдаче он спроектирован в BPMN. Код обучения есть, исполнитель процесса и внешние интеграции ещё нужны. |
| Почему локально 64 теста, а в обычном pytest меньше? | По умолчанию исключён один slow-тест обучения на 5 000 строках. Полный набор включает его; это всё ещё smoke, а не обучение на всём датасете. |
| Почему решение человека обязательно? | Отказ и лишнее обслуживание имеют производственные последствия; метрики не подтверждают доступность признаков и применимость к конкретному парку. |
| Что делать после трёх неудач? | Остановить автоматические повторы, сохранить действующую версию, исследовать данные и признаки; возобновить после решения ответственного. |
| Что является моей доработкой? | Исправления входных проверок, риска, PSI, сохранности MLflow, настройки окружения/CI, корректировка карточки, два процесса и материалы защиты. База взята из группового проекта. |
