## Текст выступления

**[Открыть README.]**

Здравствуйте. Мы представляем учебный проект по прогнозированию отказов
промышленного оборудования. Меня зовут Сергей Скрипин; в команде я отвечаю
за проект в целом, воспроизводимое окружение, pre-commit, линтеры и CI.
Александр Яньшин представит карточку модели, Ильдар Исангузин — жизненный
цикл модели, Андрей Фер — процесс переобучения.

Пайплайн пакетный. Он загружает `train.csv` и `test.csv`, проверяет схему,
строит 17 признаков, обучает CatBoost, сохраняет метрики и графики, пишет
эксперимент в MLflow, затем оценивает `test.csv` и формирует CSV с
рекомендациями. Данные синтетические, из Kaggle Playground S3E17. В baseline
входят флаги уже произошедшего отказа, поэтому это учебная классификация
состояния, а не доказанное раннее предупреждение. Ограничения и метрики
подробно разобраны в карточке.

**[Показать `src`, `pyproject.toml`, `poetry.toml`, `.gitignore`.]**

Первое задание — подготовить проект к сопровождению. В исходной версии уже
были отдельные модули загрузки, признаков, обучения, инференса и мониторинга.
Я сохранил эту структуру и проверил работу на границах модулей. Исправления
касались конкретных контрактов: проверка входных данных теперь отклоняет
бесконечные значения, небинарные флаги и цель, неизвестный `Type`, дубли
идентификаторов и пустой пакет. Категории риска не падают при одинаковых
квантилях. PSI строит границы по reference, учитывает минимальное значение и
сглаживает нулевые частоты. При конфликте путей MLflow сохраняет историю и
выдаёт понятную ошибку вместо удаления базы. Дополнительно исправлены отчёты
для малых пакетов и остановка пайплайна после ошибки обучения.

Poetry управляет зависимостями и создаёт `.venv` внутри проекта.
`pyproject.toml` описывает зависимости и dev-группу, `poetry.lock` фиксирует
версии, `poetry.toml` задаёт локальное окружение. Команда
`poetry sync --with dev` восстанавливает окружение, `poetry check --lock`
проверяет согласованность конфигурации и lock-файла. Сам `.venv` исключён из
Git: на другой машине он восстанавливается из lock-файла. В отличие от
простого `venv`, Poetry дополнительно разрешает зависимости и фиксирует их.

**[Открыть `.pre-commit-config.yaml` и `.github/workflows/ci.yml`.]**

Перед коммитом pre-commit запускает Black, isort и Flake8. Black форматирует
код, isort упорядочивает импорты, Flake8 находит нарушения стиля и часть
ошибок, включая предупреждения flake8-bugbear. Дополнительные хуки проверяют
хвостовые пробелы, конец файла, YAML, TOML, большие файлы, конфликтные маркеры
и приватные ключи. Версии инструментов в хуках закреплены теми же релизами,
что и в `pyproject.toml`; поэтому локальный и CI-прогоны не расходятся.
Установка хуков — `poetry run pre-commit install`.

CI повторяет эти проверки и запускает тесты. Задача lint выполняет
`pre-commit run --all-files`; задача test проверяет Python 3.11, 3.12 и 3.13
с `poetry sync` и pytest с покрытием; после них Docker-задача собирает образ
и выполняет smoke-обучение и инференс. Полный CI для снимка `e13ae9e`
завершился успешно. Локально обычный `pytest` даёт 74 теста, а с
`--override-ini addopts=''` — 75, потому что добавляется slow smoke-тест
обучения. Инференс на `test.csv` выдал 90 954 прогноза; меток в этом файле
нет, поэтому проверен контракт программы, а не качество модели.

Передаю слово Александру Яньшину — карточка модели.

## Перед демонстрацией

1. Открыть терминал в корне репозитория и проверить ветку:
   `git branch --show-current`. Для командной защиты используется `main` после
   слияния PR #17; если преподаватель просит исходную ветку, переключиться на
   `yanshin`.
2. Заранее открыть в редакторе `README.md`, `pyproject.toml`, `poetry.toml`,
   `.pre-commit-config.yaml`, `.github/workflows/ci.yml` и `Dockerfile`.
3. Не запускать полный CI и Docker на сцене: они долгие. Показать уже
   сохранённый успешный результат, а команды выполнить только по просьбе.
4. Проверить, что окружение восстановлено: `poetry env info --path`.

```powershell
poetry check --lock
poetry env info --path
poetry run pre-commit run --all-files
poetry run pytest -q
poetry run pytest -q --override-ini addopts=''
```

Последняя команда включает slow smoke-тест обучения и может занимать заметно
больше времени. Если она не запускалась после последних изменений, не выдавать
её результат за уже выполненный.

## Короткие ответы на возможные вопросы

| Вопрос | Короткий ответ |
| --- | --- |
| Зачем Poetry, если можно создать `venv` вручную? | Poetry одновременно разрешает зависимости, фиксирует их в `poetry.lock` и создаёт локальное окружение. `venv` сам по себе не гарантирует одинаковые версии на другой машине. |
| Почему `.venv` не хранится в Git? | Это машинозависимый каталог с бинарными пакетами. Воспроизводимость обеспечивают `pyproject.toml` и `poetry.lock`, а не копия окружения. |
| Что именно делает pre-commit? | Запускает хуки до коммита: форматирование, сортировку импортов, линтер и проверки файлов. Хук можно обойти, но CI всё равно выполнит те же проверки. |
| Чем Black отличается от Flake8? | Black только форматирует код и не ищет логические ошибки; isort упорядочивает импорты; Flake8 проверяет стиль и подозрительные конструкции. Они дополняют друг друга. |
| Зачем `flake8-bugbear`? | Он добавляет эвристики для конструкций, которые часто приводят к ошибкам. Это не замена тестам, а дополнительный статический сигнал. |
| Почему версии хуков закреплены точно? | Иначе локальный Black или Flake8 мог бы отличаться от CI и менять результат при одном и том же коде. Версии синхронизированы с dev-группой Poetry. |
| Почему тесты идут на Python 3.11–3.13? | `pyproject.toml` разрешает этот диапазон; матрица CI проверяет совместимость, а не только одну локальную версию. |
| Зачем отдельная Docker-задача, если тесты уже прошли? | Она проверяет сборку образа и запуск обучения/инференса в контейнере. Успешные Python-тесты не доказывают, что Docker-образ работает. |
| Что именно изменено в первом задании? | Усилены контракты данных, обработка квантилей и PSI, сохранность истории MLflow, конфигурация путей, отчёты для малых пакетов и остановка пайплайна при ошибке обучения. Исходная модульная структура сохранена. |
| Это полностью ваш код? | Нет. Основа — групповой проект; вклад команды и границы доработки разделены в `docs/assignments.md` и истории Git. Мы не приписываем себе исходную разработку. |
| Тесты hh.ru пройдены? | В материалах нет подтверждающих скриншотов, поэтому результат не заявляется. Это отдельный личный этап. |
| Почему на сцене не запускается полный CI? | Он включает матрицу трёх версий Python и Docker smoke и занимает слишком много времени. Показывается сохранённый успешный прогон; команды можно повторить после защиты. |
