## Обязательные вопросы аудита

- Нет ли утечки через TWF/HDF/PWF/OSF/RNF и счётчик? Правильно ли описаны
  предобработка до split, early stopping и отсутствие временной независимой оценки?
- Не смешаны ли исторический full run, новый smoke, исследовательская CV и test
  без меток? Не представлены ли вероятности как откалиброванные?
- Корректны ли PSI на постоянных/раздельных распределениях, одинаковые оценки
  риска, пустые/некорректные входы, значения NaN/Infinity и JSON-отчёты?
- Сохраняется ли MLflow-история при конфликте пути? Не удаляют ли её вспомогательные
  скрипты, не продолжается ли инференс после ошибки обучения?
- Работают ли документированные переменные окружения? Изолированы ли проверки
  от прежних артефактов и рабочих экспериментов?
- Выполнимы ли условия BPMN? Нельзя ли обойти одобрение, зациклить повторы,
  опубликовать несовместимую версию или потерять возможность отката?
- Совпадает ли логика XML, Mermaid и текста? Какие исключения раскрыты только
  в тексте? Не маскирует ли `isExecutable=false` заявление о действующей автоматизации?
- Есть ли числовые критерии, источник которых не обозначен? Не выдаются ли
  проектные допущения или гипотетический экономический эффект за измеренные результаты?
- Есть ли в зависимостях, скриптах, CI или инструкции воспроизводимые сбои,
  которые существующие тесты пропускают? Отдели исходные дефекты от новых регрессий.

## Как воспроизвести проверки

После осмотра кода, в отдельной копии репозитория с Python 3.11–3.13 и Poetry 2.x:

```powershell
git clone --branch yanshin https://github.com/svscrip/auto_ML_prediction_fail_new.git
cd auto_ML_prediction_fail_new
git rev-parse HEAD
git diff 41b06a6431a4bf8db9b21590e81f93269ebde71d HEAD --stat
poetry sync --with dev
poetry run python scripts/review_project.py verify
```

Команда запускает проверку lock-файла, Black/isort в режиме проверки, Flake8,
весь pytest (включая slow; тесты обучения пишут только во временные каталоги),
сверку карточки, отдельное smoke-обучение на 2 000 строках и инференс этой
моделью на полном test.csv.
Полный ablation-эксперимент команда `verify` не повторяет; для него предусмотрена
команда `poetry run python -m src.ablation`. Проверки подтверждают инварианты
его кода, состав разбиения и согласованность опубликованных чисел.
Проверяются идентификаторы, количество прогнозов, диапазон вероятностей и
валидность JSON. Для каждой проверки записываются команда, код выхода и лог.
Создаётся отдельное хранилище MLflow в `artifacts/review/verification-*/runtime`.
Скрипт не устанавливает пакеты, не меняет ветки и не выполняет деплой.
Отсутствующая команда и тайм-аут считаются неуспешной проверкой.

Отдельно: `poetry run pre-commit run --all-files` может форматировать файлы,
поэтому выполнять в копии. Docker проверяется отдельной задачей
[CI для yanshin](https://github.com/svscrip/auto_ML_prediction_fail_new/actions/workflows/ci.yml?query=branch%3Ayanshin).
Проверить SHA конкретного запуска, не переносить успех старого CI на новый код.
Скрипт проверки сам Docker не запускает. `reset-mlflow.ps1` можно осмотреть
через `-WhatIf`; архивирование реально существующей истории для аудита не требуется.

## Пакет для модели без доступа к GitHub

```powershell
poetry run python scripts/review_project.py bundle --verification artifacts/review/verification-ИМЯ_ПРОГОНА
```

Путь берётся из вывода `verify`. Команда откажется собирать пакет, если файлы
изменились после проверки. Результат в `artifacts/review/packet-*`:

- `AI_REVIEW_PACKET.txt` — запрос, исходники, документация, метаданные и протокол
  для загрузки в чат. Полные CSV, lock-файл и изображения в текст не вставляются.
- `yanshin-review.zip` — те же материалы в папке `project/`, также CSV, lock,
  схемы, логи, JUnit, diff и контрольные суммы. Пакет отобран по явному списку;
  `.git`, окружение, секреты, результаты обучения и видео не включены.
- `manifest.json` — SHA снимка и SHA-256 каждого включённого файла.
- `verification.json` — фактически выполненные проверки, статус и ограничения.

Ничего автоматически не отправляется внешним сервисам. Передай пакет выбранной
модели сам. Если модель не читает ZIP, загрузи TXT; для проверки расчётов и данных
потребуются CSV/JSON из ZIP или доступ к репозиторию.

## Требуемый формат независимого заключения

1. Проверенный SHA, способ доступа, какие файлы/команды фактически проверены.
2. Таблица ДЗ 1 / ДЗ 2 / ДЗ 3 / защита: **соответствует / частично / не соответствует / не проверено**.
3. Замечания по убыванию важности: P1 — мешает работе/сдаче или искажает выводы;
   P2 — существенный дефект сопровождения; P3 — улучшение. Для каждого — доказательство.
4. Отдельные заключения: «воспроизводимость кода», «учебные требования»,
   «готовность модели к промышленному применению». Не заменять одно другим.
5. Что исправить до сдачи, что можно оставить как явное ограничение и что нельзя
   проверить без внешних данных. Не выставлять оценку за отсутствующие скриншоты hh.ru.
